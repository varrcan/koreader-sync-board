# Вход через OIDC

[English](../oidc.md) | Русский

Панель может пускать пользователей через одного провайдера OpenID Connect (Zitadel, Keycloak,
Authentik …) по Authorization Code flow с PKCE. KOReader это не затрагивает: читалки по-прежнему
используют пароли устройств. OIDC включается тремя переменными:

```sh
docker run ... \
  -e KSB_OIDC_ISSUER=https://id.example.com \
  -e KSB_OIDC_CLIENT_ID=123456789@books \
  -e KSB_PUBLIC_URL=https://books.example.com \
  -e KSB_OIDC_NAME=Zitadel \
  ghcr.io/varrcan/koreader-sync-board:latest
```

Все переменные OIDC перечислены в разделе [Настройка](configuration.md#oidc). Зарегистрируйте у
провайдера **redirect URI**:

```
https://books.example.com/api/v1/auth/oidc/callback
```

`KSB_PUBLIC_URL` — адрес, по которому пользователи открывают панель: только origin
(`https://host` или `http://host:port`), без пути. Панель под префиксом пути не поддерживается.
Если панель открыли по другому адресу (IP в локальной сети, `localhost`), кнопка входа сначала
отправит на `KSB_PUBLIC_URL`, и весь вход пройдёт там; привязка учётной записи (см. ниже)
работает только по публичному адресу, и панель показывает ссылку на него.

При старте сервер к провайдеру не обращается: discovery выполняется при первом входе. Если
провайдер недоступен, вход завершается сообщением об ошибке и повторяется в следующий раз, а
сервер и синхронизация KOReader продолжают работать.

## Кого пускать

Пользователь панели связывается с учётной записью у провайдера по issuer и `sub`, а не по
имени или email. Связать их можно двумя способами:

- существующий пользователь входит с паролем панели, открывает **Учётную запись** и нажимает
  **Привязать**; **Отвязать** удаляет связь (только если у пользователя есть пароль панели);
- с `KSB_OIDC_AUTO_CREATE=true` первый вход неизвестной учётной записи провайдера создаёт
  пользователя панели с именем из claim `preferred_username` (`KSB_OIDC_USERNAME_CLAIM`), без
  пароля панели и без устройств. Если имя уже занято, вход отклоняется, а существующий
  пользователь остаётся нетронутым — войдите под ним с паролем и привяжите учётную запись.
  Пользователь, созданный так, может задать пароль панели в **Учётной записи**.

Первый администратор по-прежнему создаётся мастером первого запуска или через
`ADMIN_USER`/`ADMIN_PASSWORD`; до этого вход через OIDC отклоняется. Кого вообще пускать, решает
провайдер (например, каким пользователям в Zitadel выдан доступ к проекту).

## Роль администратора из claim

Если заданы `KSB_OIDC_ADMIN_CLAIM` и `KSB_OIDC_ADMIN_VALUE`, каждый вход через OIDC (и привязка)
делает пользователя `admin`, если claim в ID-токене совпадает, и `user` в противном случае; смена
роли пишется в лог. Совпадением считается строка, равная значению, массив, который его содержит,
или объект с таким ключом. Без этих переменных OIDC роли не меняет. Если провайдер по ошибке
лишил роли, верните её командой `ksb user role alice admin` (следующий вход через OIDC снова
применит claim).

## Отключение входа по паролю

`KSB_PANEL_PASSWORD_LOGIN=false` (только вместе с OIDC) отключает пароль панели для
пользователей, **привязанных** к провайдеру; пользователи без привязки по-прежнему входят с
паролем, так что запереть себя не получится. Безопасный порядок:

1. создайте администратора мастером первого запуска или через `ADMIN_USER`/`ADMIN_PASSWORD`;
2. войдите с паролем и привяжите учётную запись провайдера в **Учётной записи**;
3. перезапустите с `KSB_PANEL_PASSWORD_LOGIN=false`.

Выход из панели завершает только сессию панели, а не сессию у провайдера. Отключение
пользователя у провайдера не закрывает его открытые сессии в панели: для этого есть
`ksb user disable`.

## Смена issuer

Привязки связаны с URL issuer. После смены `KSB_OIDC_ISSUER` (новый домен провайдера) старые
привязки перестают совпадать: удалите их командой `ksb user oidc-unlink alice` и привяжите
заново.

## Zitadel

1. В проекте создайте приложение типа **Web**: метод аутентификации **PKCE** (без секрета) или
   **Code** (тогда задайте `KSB_OIDC_CLIENT_SECRET`). Добавьте redirect URI, указанный выше.
2. В настройках токенов приложения включите **User Info inside ID Token** (имя пользователя
   берётся из ID-токена) и, для claim с ролью, **User roles inside ID Token**.
3. Для claim с ролью включите в проекте **Assert Roles on Authentication**, создайте роль
   (например, `admin`) и выдайте её администраторам. Затем задайте

   ```sh
   KSB_OIDC_ADMIN_CLAIM=urn:zitadel:iam:org:project:roles
   KSB_OIDC_ADMIN_VALUE=admin
   ```

`KSB_OIDC_ISSUER` — URL инстанса, например `https://id.example.com`; client ID указан на странице
приложения. Для Keycloak или Authentik так же работает claim `groups`:
`KSB_OIDC_ADMIN_CLAIM=groups`, `KSB_OIDC_ADMIN_VALUE=ksb-admins`.
