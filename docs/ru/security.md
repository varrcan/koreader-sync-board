## Неудачные входы

После **10 неудачных входов за 10 минут** с одного адреса клиента этот адрес блокируется на
**15 минут**. Входы KOReader (синхронизация прогресса, WebDAV и OPDS), входы в панель (неверный
пароль, в том числе текущий пароль при его смене) и неверные коды настройки расходуют общий
лимит. Клиенты IPv6 считаются по сети `/64`. Счётчики хранятся в памяти и сбрасываются при
перезапуске.

- KOReader показывает причину: *«Too many failed attempts. Try again in N minutes.»* (статус
  401, код 2001, плюс заголовок `Retry-After` для других клиентов). Заблокированный
  `POST /users/create` получает 402/2005 с похожим текстом.
- Устройство, которое недавно входило, продолжает синхронизироваться с заблокированного адреса:
  сервер помнит успешную проверку и продлевает её с каждым запросом.
- Повтор **того же** неверного пароля (например, забытой читалкой, чьё устройство отозвали)
  получает ответ сразу и не расходует лимит, поэтому не может заблокировать другие читалки в той
  же домашней сети.
- При включённой регистрации каждый `POST /users/create` считается попыткой, успешные тоже.
- Панель отвечает заблокированному адресу `429 Too Many Requests` и `Retry-After`. В отличие от
  KOReader, повторный неверный пароль панели считается каждый раз.
- Неудачные входы через OIDC не считаются и пишутся в лог как `panel: oidc login failed` с
  `reason`, а не как `authorization failed`: отказ у провайдера — не подбор пароля.

## За обратным прокси

Синхронизация прогресса, WebDAV и OPDS передают пароль устройства в каждом запросе (OPDS и
WebDAV — как HTTP Basic), поэтому за пределами домашней сети отдавайте их по HTTPS через
обратный прокси.

За nginx, nginx proxy manager, Caddy или Traefik каждый запрос приходит с адреса прокси.
Сообщите серверу, какие адреса принадлежат вашему прокси, чтобы он брал адрес клиента из
`X-Forwarded-For`:

```sh
docker run ... -e KSB_TRUSTED_PROXIES=172.17.0.0/16 ghcr.io/varrcan/koreader-sync-board:latest
```

Указывайте **только сам прокси** (его адрес или сеть Docker, из которой он обращается к серверу).
Заголовок читается справа налево, и первый адрес, не являющийся доверенным прокси, считается
клиентом; для запроса с недоверенного адреса заголовок игнорируется. Прокси должен дописывать
адрес клиента, как nginx с `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`
(nginx proxy manager делает это по умолчанию).

Ошибка в `KSB_TRUSTED_PROXIES` обходится дорого в обе стороны:

- **не задано** за прокси: все клиенты делят адрес прокси, поэтому один атакующий блокирует вход
  всем, чьё устройство недавно не входило, а в логе виден только прокси;
- **слишком широко** (например, `0.0.0.0/0`): любой клиент может подставить в `X-Forwarded-For`
  произвольный адрес и обойти лимит.

Кроме того, прокси должен:

- передавать исходный заголовок `Host` (nginx: `proxy_set_header Host $host;`; nginx proxy
  manager, Caddy и Traefik делают это по умолчанию). Панель отклоняет вход и другие изменения с
  чужого сайта; по обычному `http://` браузеры не отправляют `Sec-Fetch-Site`, поэтому сервер
  сравнивает `Origin` с `Host`, и переписанный `Host` приводит к ошибке `cross_origin` при каждом
  входе;
- сохранять заголовок ответа `ETag` и заголовок запроса `If-Match` на `/dav/` и пропускать тела
  запросов до 64 МиБ (nginx: `client_max_body_size 64m;`). Без `ETag` KOReader выгружает файл без
  `If-Match`, получает `412` и повторяет бесконечно.

## fail2ban

Каждый неудачный вход пишется в лог одной JSON-строкой с адресом клиента:

```json
{"time":"2026-11-04T21:47:10.84+03:00","level":"WARN","msg":"kosync: authorization failed","user":"alice","ip":"198.51.100.7","path":"/users/auth","reason":"unauthorized"}
{"time":"2026-11-04T21:48:02.11+03:00","level":"WARN","msg":"panel: authorization failed","user":"alice","ip":"198.51.100.7","path":"/api/v1/auth/login","reason":"unauthorized"}
{"time":"2026-11-04T21:49:31.52+03:00","level":"WARN","msg":"webdav: authorization failed","user":"alice","ip":"198.51.100.7","path":"/dav/statistics.sqlite3","reason":"unauthorized"}
{"time":"2026-11-04T21:50:12.03+03:00","level":"WARN","msg":"opds: authorization failed","user":"alice","ip":"198.51.100.7","path":"/opds","reason":"unauthorized"}
```

Повторы уже отклонённого пароля, запросы, отклонённые из-за блокировки, и запросы OPDS без
пароля (многие клиенты сначала пробуют так) в лог не пишутся. Чтобы банить настойчивых
нарушителей надолго, создайте `/etc/fail2ban/filter.d/ksb.conf`:

```ini
[Definition]
# Подходит и для обычной JSON-строки, и для json-file лога Docker, где кавычки экранированы.
failregex = \\?"msg\\?":\\?"(?:kosync|panel|webdav|opds): authorization failed\\?".*\\?"ip\\?":\\?"<HOST>\\?",\\?"path\\?"
datepattern = "time\\?":\\?"%%Y-%%m-%%dT%%H:%%M:%%S(?:\.\d+)?%%z
```

и `/etc/fail2ban/jail.d/ksb.local`:

```ini
[ksb]
enabled  = true
filter   = ksb
# Драйвер json-file Docker по умолчанию; для бинарника под systemd вместо этого
# backend = systemd и journalmatch = _SYSTEMD_UNIT=ksb.service.
logpath  = /var/lib/docker/containers/*/*-json.log
maxretry = 30
findtime = 1h
bantime  = 1d
port     = http,https
# Порты, опубликованные Docker, обходят цепочку INPUT.
chain    = DOCKER-USER
```

Банить нужно на хосте, который принимает соединения клиентов: при обратном прокси — на хосте
прокси. Проверьте фильтр на своём логе командой
`fail2ban-regex /var/lib/docker/containers/<id>/<id>-json.log /etc/fail2ban/filter.d/ksb.conf`.
